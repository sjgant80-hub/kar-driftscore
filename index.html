Start here

DriftScore answers one question: has the mix of things my model is dealing with changed, and by how much? That mix is a distribution — a count of how often each category shows up.

  1. Count your categories, then and now. Pick anything with categories: the labels your classifier predicts, the intents your router picks, the regions your users come from, the error codes your service returns. Count them over a baseline window (when things were healthy) and over a current window (now).
  2. Paste both counts above — one label: count per line — and press Compute drift score.
  3. Read the number. 0 means the two windows are identical. 1 means they share nothing. The table shows exactly which category moved the needle.
  4. Set your own line. DriftScore reports the distance honestly; you decide the threshold that trips an alert (a common starting point is 0.1–0.2 for "worth a look"). It is the same number every time, so a threshold you pick today still means the same thing next quarter.

How it works

The score is the total variation distance between two probability distributions — a textbook, hundred-year-old statistic, not a heuristic we invented. Here is the whole mechanism, start to finish.

Traced through a real run

The "Sentiment classifier drifted" example above:

baseline = { positive: 820, neutral: 150, negative: 30 }   total 1000
current  = { positive: 540, neutral: 250, negative: 210 }   total 1000

normalise →   positive  neutral  negative
   baseline     0.820    0.150    0.030
   current      0.540    0.250    0.210
   |Δ prob|     0.280    0.100    0.180      Σ = 0.560

drift = 0.560 / 2 = 0.280

Negative sentiment went from 3% of traffic to 21% — a real shift a monitoring team would want to catch. DriftScore puts a defensible number on it: 0.28. Halving the sum is what keeps the answer in 0..1: every unit of probability that leaves one label has to arrive at another, so each real move is counted twice in the sum.

Why it refuses to lie

The kernel is total: hand it garbage and it returns {ok:false, why:"…"} instead of throwing or guessing. Negative counts, NaN, a distribution that sums to zero, a non-object — each is rejected with a plain reason. That matters because a drift monitor that silently returns 0 on bad input is worse than no monitor: it reports "all calm" over a broken feed.

This is also where the proof-of-play bit its teeth. Correctness tests alone — "identical scores 0", "disjoint scores 1" — left half the mutations of this kernel alive. Only tests pinned to the exact boundaries killed them all: that count < 0 rejects but count = 0 is valid; that a total of exactly 0 is rejected while any positive total passes; that the finite-number check uses and not or so NaN can't slip through; that the error strings are verbatim. Eleven mutants, eleven killed, nothing baselined. That is the whole point of the gate — green because it was attacked, not because nobody looked.

Blueprint — how it's built, organ by organ

kernel.mjs
~70 lines of pure functions: normalize() and driftScore(). No I/O, no dependencies, no global state. This is the whole brain.
kernel.test.mjs
12 tests — the behaviour contract and the boundary probes that close the mutation gate.
witness.mjs
The mutation gate. It rewrites the kernel 11 ways (flip a < to <=, an && to ||, a return value) and demands the tests catch every one. A survivor means a test is missing.
runner.mjs
A supervisor that holds the test process under a hard time bound and takes its whole process tree down on timeout — so the gate can't be fooled by a hung child reported as green.
index.html this page
A single-file PWA. The exact bytes of kernel.mjs are inlined and loaded at runtime, and a CI parity test fails the build if they ever drift from the gated source. So the number you see above is produced by the code that passed the gate — not a re-implementation of it.
CI
GitHub Actions runs the tests, the mutation gate, and the parity check on every push. Green on GitHub's own runner is the un-forgeable proof.

Adoption — rolling it into your stack

  1. Pick your signal. The highest-value one is usually your model's own output: the distribution of predicted classes, routed intents, or tool calls. Input features work too (categorical ones directly; bucket numeric ones into bins first).
  2. Snapshot a baseline. Count that signal over a window you're happy with — a golden week, the validation set, last month. Store the counts (a tiny JSON blob).
  3. Score on a schedule. In your monitoring job, count the same signal over the recent window and call driftScore(baseline, current). It's one pure function — drop kernel.mjs into Node, or port the ~40 lines to Python/Go in an afternoon; the maths is standard.
  4. Alert on your threshold, keep the receipt. Store the score and both distributions with each run. When drift trips an alert, the receipt is self-verifying: anyone can recompute the number and see exactly which category moved.
  5. Scale out. One score per signal, per segment, per model version. Because it's deterministic and offline, you can run thousands of these for the cost of counting — no inference, no API bill.

Risks, answered straight

"It's just one metric."
Correct, by design. Total variation distance measures how much a categorical distribution moved, not why or whether it's statistically significant. Use it as the fast, cheap, always-verifiable first line; pair it with a significance test or feature attribution when an alert fires.
"What about numeric features?"
Bucket them into bins first (DriftScore scores the bin distribution). For continuous distributions you may prefer a dedicated metric (KS statistic, PSI); DriftScore's strength is categorical and prediction drift.
"Thresholds are subjective."
Yes — and that's honest. DriftScore won't invent an alert line for you. Because the score is deterministic, a threshold you calibrate once keeps meaning the same thing forever.

White paper — the one-page version

Problem. A deployed model is only as good as the assumption that today's data looks like the data it was validated on. When the mix of inputs or outputs shifts — a new user segment, a seasonal swing, an upstream change — accuracy can degrade silently. Teams need to detect this, but the common answer is a monitoring SaaS whose "drift" number is proprietary, metered, and computed on data you had to ship to a vendor.

Approach. DriftScore reduces drift detection to its defensible core: the total variation distance between two categorical distributions, ½·Σ|pₐ−p_b|, bounded in [0,1]. It is deterministic (same inputs, same output, forever), total (malformed input is rejected with a reason, never silently zeroed), and dependency-free. The logic is proven by a mutation gate — every one-line corruption of the kernel is caught by a test — and the live page runs the exact gated bytes, verified byte-identical in CI.

Why it's trustworthy. Trust here is not a brand promise; it's a property. Because the number is deterministic and the code is ~70 readable lines with no I/O, any party — your team, an auditor, a regulator — can recompute a drift alert from the raw counts and get the same answer. The monitoring decision stops depending on a vendor's black box.

Limits. DriftScore measures magnitude of categorical/prediction drift, not statistical significance or root cause, and is not a substitute for a full monitoring platform's dashboards and pipelines. It is the primitive at the centre, done honestly, that you own.
